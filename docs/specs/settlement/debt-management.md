# Debt Management

## Context
Settlement bounded context. Manages the debts generated when porras are resolved — who owes whom, how much, and in what currency. Replaces the old balance-based model: there are no fictional points, no initial balance, and no one gets blocked.

## Description
When a porra is resolved, the system generates individual debts from each loser to the winner(s). Debts are tracked per porra (granular) with consolidated summary views (net position between any two members). Debts exist until the receiver confirms payment. The payer can request marking a debt as paid.

## Domain model

### Entities
- **Debt** — aggregate root. Represents a single debt from one member to another, generated by a specific porra resolution. Lifecycle: pending → payment_requested → paid.

### Value objects
- **DebtId** — UUID, generated server-side.
- **Amount** — positive decimal, the money owed.
- **Currency** — the group's configured currency. Stored as a symbol/emoji (e.g., "€", "🍺"). Default: "€".
- **DebtStatus** — enum: PENDING, PAYMENT_REQUESTED, PAID.
- **ConsolidatedDebt** — read projection. Net amount between two members across all porras in a group.

### Domain events
- `DebtGenerated` — emitted when a porra is resolved. Carries: debtId, groupId, porraId, fromMemberId, toMemberId, amount, currency, occurredAt.
- `PaymentRequested` — emitted when the payer requests to mark a debt as paid. Carries: debtId, requestedBy, occurredAt.
- `DebtSettled` — emitted when the receiver confirms payment. Carries: debtId, confirmedBy, occurredAt.

## Rules and invariants

1. Debts are generated automatically when a porra is resolved (one debt per loser→winner pair).
2. Each debt is tied to a specific porra — never merged at the domain level.
3. Only the **payer** (fromMember) can request marking a debt as paid.
4. Only the **receiver** (toMember) can confirm and settle the debt.
5. A settled debt cannot be reopened.
6. Debts use the group's configured currency.
7. When a porra is cancelled or refunded, no debts are generated (or existing ones are voided).
8. Consolidated views (net position between two members) are read-only projections, not domain state.

## Debt generation logic

### Binary and multiple choice porras
- Losers each owe the stake amount.
- The total pot (losers × stake) is distributed to winner(s).
- **Single winner:** each loser owes `stake` to the winner.
- **Multiple winners (split):** each loser owes `stake` total, split across winners. If uneven, remainder distributed to random winner(s).

### Numeric porras
- Same as above, but winners are determined by the numeric resolution rules (tolerance, closest to result).
- If nobody wins (nobody within margin), no debts generated — porra resolves with no financial impact.

### Example: 4 players, stake=10€, 1 winner
- Alice (winner), Bob, Carol, Dave (losers).
- Debts: Bob→Alice 10€, Carol→Alice 10€, Dave→Alice 10€.

### Example: 4 players, stake=10€, 2 winners
- Alice and Bob (winners), Carol and Dave (losers).
- Pot = 20€ (2 losers × 10€). Split between 2 winners = 10€ each.
- Debts: Carol→Alice 5€, Carol→Bob 5€, Dave→Alice 5€, Dave→Bob 5€.

## Commands and queries

### Commands (write operations)
| Command | Input | Output | Rules applied |
|---------|-------|--------|---------------|
| GenerateDebts | groupId, porraId, winners, losers, stake, currency | list of debtIds | 1, 2, 6 |
| RequestPayment | debtId, requesterId | void | 3 |
| SettleDebt | debtId, confirmerId | void | 4, 5 |

### Queries (read operations)
| Query | Input | Output | Notes |
|-------|-------|--------|-------|
| GetDebtsByPorra | porraId | list of debts | Per-porra view |
| GetMyDebts | groupId, memberId | debts I owe + debts owed to me | Personal debt view |
| GetConsolidatedDebts | groupId, memberId | net position with each other member | Summary view |
| GetGroupDebtSummary | groupId | all pending debts consolidated | Group-wide summary |

## Behavior

### Happy path (resolution → debts → payment)
1. Resolution context emits `ResolutionAccepted`.
2. Settlement generates debts (one per loser→winner).
3. `DebtGenerated` events emitted.
4. Bob (loser) pays Alice (winner) via Bizum outside the app.
5. Bob requests payment confirmation in the app (`PaymentRequested`).
6. Alice confirms receipt (`DebtSettled`).

### Consolidated view example
Bob owes Alice 10€ from porra 1, Alice owes Bob 5€ from porra 2.
- Per-porra view: two separate debts.
- Consolidated view: "Bob owes Alice 5€ net".

### Edge cases
| Case | Trigger | Expected behavior |
|------|---------|-------------------|
| Porra cancelled | PorraCancelled event | No debts generated. If debts existed from a previous (voided) resolution, they are voided. |
| No winners (numeric, nobody in margin) | ResolutionAccepted with empty winners | No debts generated |
| Winner leaves group | Winner left with pending debts owed to them | Debts remain — they can still be settled. Leaving doesn't erase what others owe you. |
| Loser leaves group | Loser left with pending debts | Debts remain — leaving doesn't erase what you owe. |
| Payment requested, receiver ignores | Payer requested, no confirmation | Debt stays in PAYMENT_REQUESTED. No timeout — receiver confirms when ready. |
| Uneven split | 3 losers, 2 winners, stake=10€ | Pot=30€. Per winner=15€. Each loser owes 5€ to each winner. Total per loser = 10€ ✓ |

## Acceptance criteria

1. GIVEN a resolved porra with 1 winner and 3 losers, stake=10€ WHEN GenerateDebts is executed THEN 3 `DebtGenerated` events are emitted (one per loser, each for 10€ to the winner).
2. GIVEN a resolved porra with 2 winners and 2 losers, stake=10€ WHEN GenerateDebts is executed THEN 4 debts are generated (each loser owes 5€ to each winner).
3. GIVEN a pending debt WHEN the payer calls RequestPayment THEN `PaymentRequested` is emitted.
4. GIVEN a pending debt WHEN the receiver calls RequestPayment THEN it is rejected (only the payer can request).
5. GIVEN a PAYMENT_REQUESTED debt WHEN the receiver calls SettleDebt THEN `DebtSettled` is emitted and status becomes PAID.
6. GIVEN a PAYMENT_REQUESTED debt WHEN the payer calls SettleDebt THEN it is rejected (only the receiver can confirm).
7. GIVEN a cancelled porra WHEN debts are checked THEN no debts exist for that porra.
8. GIVEN a numeric porra with no winners WHEN resolution is accepted THEN no debts are generated.
9. GIVEN Bob owes Alice 10€ (porra 1) and Alice owes Bob 5€ (porra 2) WHEN GetConsolidatedDebts is queried for Bob THEN it shows "Bob owes Alice 5€ net".

## API contract

### GET /api/groups/{groupId}/debts/mine
Response (200):
```json
{
  "iOwe": [
    {
      "debtId": "uuid",
      "porraId": "uuid",
      "porraTitle": "¿Quién gana la liga?",
      "toMember": { "userId": "uuid", "email": "alice@example.com" },
      "amount": 10.00,
      "currency": "€",
      "status": "PENDING",
      "createdAt": "2026-03-25T15:00:00Z"
    }
  ],
  "owedToMe": [
    {
      "debtId": "uuid",
      "porraId": "uuid",
      "porraTitle": "¿Cuántos goles?",
      "fromMember": { "userId": "uuid", "email": "bob@example.com" },
      "amount": 5.00,
      "currency": "€",
      "status": "PAYMENT_REQUESTED",
      "createdAt": "2026-03-24T10:00:00Z"
    }
  ],
  "consolidated": [
    {
      "withMember": { "userId": "uuid", "email": "alice@example.com" },
      "netAmount": -5.00,
      "currency": "€",
      "direction": "I_OWE"
    }
  ]
}
```

### POST /api/debts/{debtId}/request-payment
Response (200):
```json
{ "message": "Payment confirmation requested" }
```
Errors: 403 (not the payer), 400 (already settled)

### POST /api/debts/{debtId}/settle
Response (200):
```json
{ "message": "Debt settled" }
```
Errors: 403 (not the receiver), 400 (already settled, not yet requested)

## Dependencies
- **Resolution context** (upstream): consumes `ResolutionAccepted`, `PorraCancelled`.
- **Betting context** (upstream): consumes `PorraDeletedByCreator`.
- **Groups context** (upstream): group currency configuration.
