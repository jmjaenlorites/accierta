# Group Invitation

## Context
Groups bounded context. Invitations are the only way to add new members to a group. Any member can invite others.

## Description
Any group member can generate an invitation link or send an invitation email. The link contains a token that, when opened, either adds an existing user to the group or starts the registration flow and auto-joins after verification.

## Domain model

### Entities
- **Group** — existing aggregate. Invitation adds state to the group (pending invitations).

### Value objects
- **InvitationToken** — unique opaque token embedded in the invitation link. Has an expiration time.
- **InvitationLink** — the full URL containing the token (generated by the API layer, not the domain).

### Domain events
- `InvitationCreated` — emitted when an invitation is generated. Carries: groupId, invitedEmail (nullable — link-only invitations have no email), invitationToken, invitedBy, occurredAt.
- `InvitationSent` — emitted when an email invitation is sent via Resend. Carries: groupId, invitedEmail, invitationToken, occurredAt.
- `MemberJoined` — emitted when the invited user joins the group. Carries: groupId, memberId, occurredAt.

## Rules and invariants

1. Only group members can create invitations.
2. Invitation tokens expire after 7 days.
3. A user cannot be invited if they are already a member of the group.
4. An invitation can be a link-only (no email) or email-based (sends via Resend).
5. If the invited user is already registered and verified, clicking the link adds them directly.
6. If the invited user is not registered, clicking the link starts registration with the invitation token embedded. After email verification, auto-join happens.
7. An invitation token can only be used once.

## Commands and queries

### Commands (write operations)
| Command | Input | Output | Rules applied |
|---------|-------|--------|---------------|
| CreateInvitation | groupId, invitedEmail?, inviterId | invitationToken + link | 1, 2, 3 |
| AcceptInvitation | invitationToken, userId | void | 2, 5, 7 |

### Queries (read operations)
| Query | Input | Output | Notes |
|-------|-------|--------|-------|
| GetInvitationInfo | invitationToken | group name, inviter name, expiry status | Shown on the invitation landing page |

## Behavior

### Happy path (email invitation, new user)
1. Member creates an invitation for a friend's email.
2. System emits `InvitationCreated`, then sends email via Resend (`InvitationSent`).
3. Friend clicks the link, is not registered → redirected to registration with invitation token.
4. Friend registers (see user-registration spec), verifies email.
5. System processes `UserRegistered` + `EmailVerified` with invitation token → executes AcceptInvitation.
6. System emits `MemberJoined`.
7. Scoring context initializes the new member's balance.

### Happy path (link invitation, existing user)
1. Member generates a link-only invitation (no email).
2. Member shares the link via WhatsApp, Telegram, etc.
3. Existing verified user clicks the link → system executes AcceptInvitation directly.
4. System emits `MemberJoined`.

### Edge cases
| Case | Trigger | Expected behavior |
|------|---------|-------------------|
| Already a member | Invited user is already in the group | Reject invitation acceptance with "already a member" |
| Expired token | Token older than 7 days | Reject with "invitation expired" |
| Already used token | Token already consumed | Reject with "invitation already used" |
| Non-member invites | User not in the group tries to create invitation | Reject with authorization error |
| Invite by link, multiple people click | Link shared broadly | Only the first person to accept uses the token; others get "already used" |

## Acceptance criteria

1. GIVEN a group member WHEN CreateInvitation is executed with an email THEN an `InvitationCreated` event is emitted and an invitation email is sent via Resend.
2. GIVEN a group member WHEN CreateInvitation is executed without an email THEN an `InvitationCreated` event is emitted and an invitation link is returned (no email sent).
3. GIVEN a valid invitation token and a verified, non-member user WHEN AcceptInvitation is executed THEN a `MemberJoined` event is emitted.
4. GIVEN an expired invitation token WHEN AcceptInvitation is executed THEN it is rejected with an expired token error.
5. GIVEN a user who is already a member WHEN AcceptInvitation is executed THEN it is rejected with an "already a member" error.
6. GIVEN an already-used invitation token WHEN AcceptInvitation is executed THEN it is rejected.
7. GIVEN a new user registering through an invitation link WHEN email is verified THEN the user is automatically added to the group.
8. GIVEN a non-member WHEN CreateInvitation is executed THEN it is rejected with an authorization error.

## API contract

### POST /api/groups/{groupId}/invitations
Request:
```json
{
  "email": "friend@example.com"
}
```
Or without email (link-only):
```json
{}
```
Response (201):
```json
{
  "invitationToken": "token",
  "invitationLink": "https://accierta.app/invite/token",
  "expiresAt": "2026-04-01T10:00:00Z"
}
```
Errors: 403 (not a member), 400 (user already a member)

### GET /api/invitations/{token}
Response (200):
```json
{
  "groupName": "Fantasy Liga 24/25",
  "invitedBy": "Juan",
  "expired": false,
  "used": false
}
```
Errors: 404 (token not found)

### POST /api/invitations/{token}/accept
Response (200):
```json
{
  "groupId": "uuid",
  "message": "Joined group successfully"
}
```
Errors: 400 (expired/used token), 400 (already a member), 401 (not authenticated)

## Dependencies
- **Identity context** (upstream): user must be registered and verified.
- **Resend** (infrastructure): for sending invitation emails.
- **Scoring context** (downstream): consumes `MemberJoined` to initialize balance.
- **User registration spec** (cross-context): registration with invitation token triggers auto-join.
